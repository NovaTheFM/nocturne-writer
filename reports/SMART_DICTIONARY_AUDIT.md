# Smart-словарь: стресс-аудит и план улучшения

Дата: 13 октября 2026. Исходное приложение: commit `b337ea7`, версия 1.2.1. Проверяемый режим: **«Онлайн + словарь» / hybrid**. Код приложения во время аудита не менялся. Яндекс и Hunspell исключены из плана по требованию пользователя. Вторая проверка должна оценивать контекстную грамматику и пунктуацию.

## Результат

Текущий Smart-словарь пригоден прежде всего для опечаток. Контекстная проверка уже вызывается, но обработчик Nocturne обрезает её до исправлений отдельных слов: теряются пунктуация, регистр, удаления повторов и часть грамматики. Простое подключение второго API этого не исправит.

На независимом корпусе из **99 ошибочных предложений** LanguageTool 6.6 предложил заранее заданный правильный вариант в **70** случаях. После обработки Nocturne такой вариант остался в **46** случаях. Приложение потеряло **26** результатов провайдера; встроенный словарь добавил **2** исправления, которых провайдер не предложил. Это наличие ожидаемого варианта, а не обещание, что первый вариант меню всегда правильный.

| Тип ошибки | Ошибочных фраз | Ожидаемый вариант у LanguageTool | Ожидаемый вариант после Nocturne |
|---|---:|---:|---:|
| Орфография | 41 | 39 | 40 |
| Грамматика | 21 | 11 | 6 |
| Пунктуация | 25 | 12 | 0 |
| Регистр | 5 | 4 | 0 |
| Повторы | 5 | 4 | 0 |
| Словоупотребление | 2 | 0 | 0 |
| Всего | **99** | **70** | **46** |

На **111 правильных контрольных фразах** ложных замечаний Nocturne не было. Это результат этого корпуса, а не оценка точности на произвольной рукописи. В контролях есть диалоги, многоточие, `?!`, русский, украинский, английский и автоматическое определение языка.

Итог стресс-набора: **292 сценария, 194 PASS, 98 FAIL**. Здесь повторяются одни и те же причины на разных фразах и двух экранах; 98 не означает 98 независимых дефектов. Набор намеренно оставлен красным: он предъявляет будущей реализации полноценной проверки требования, которых текущая версия не выполняет. Существующие unit-тесты и прежний набор `smart-dictionary` проходят.

Проверка синтаксиса и контроль целостности исходников прошли. ## Как проверялось

- **210 фиксированных входов:** 99 ошибочных фраз с независимыми эталонными результатами и 111 правильных контролей. Эталон не строится из ответа проверяющего движка.
- **Реальный провайдер:** локальный HTTP-сервер LanguageTool 6.6, API v1, без Premium. С него записаны 210 исходных JSON-ответов. Регрессия воспроизводит эти реальные ответы, поэтому изменение облачных правил не меняет базовый результат.
- **Реальная HTTP-интеграция:** отдельно на ПК и мобильном браузере получен HTTP 200 от локального LanguageTool. Одновременно появляются пользовательское правило `auditlocal → story` и онлайн-исправление `adress → address`; рукопись сама не изменяется. В тесте меняется адрес транспорта; приложение продолжает иметь свой прежний endpoint.
- **Позиции:** 1000 воспроизводимых Unicode-входов, 3000 адресованных вхождений; emoji, ZWJ, комбинируемые символы, bidi-маркеры, арабский и китайский префиксы, регистр и переносы. Отдельно проверен текст около 20 тысяч символов.
- **Редактор:** два изолированных профиля, 1440 × 900 и 390 × 844 с touch-настройками. Проверены индекс замечаний, применение орфографического исправления, Undo, соседнее форматирование, защита авторского словаря и 50 быстрых правок на профиль — всего 100.
- **Сбои:** HTTP 429/500/503, разрыв сети, зависание, поздний ответ после Abort, неполный результат, отсутствие замен, повреждённые диапазоны, HTML в вариантах, вариант длиной 8192 символа, токен длиной 10 000 символов, параллельные одинаковые запросы и кэш.

Стресс-запросы не отправлялись в публичный API LanguageTool: его официальные условия запрещают автоматические запросы и рекомендуют свой сервер или Enterprise. Сейчас документированы ограничения 20 запросов/минуту, 75 KB/минуту, 20 KB/запрос и варианты лишь для первых 30 орфографических ошибок; доступность и неизменность правил не гарантируются. [Официальные условия API](https://dev.languagetool.org/public-http-api).

## Подтверждённые причины

### 1. Результат сводится к слову вместо диапазона текста

В [smart-speller.js](../src/core/smart-speller.js), `onlineMatches`, разрешены только ненулевые диапазоны из одного слова. `spellingSuggestions` принимает буквенные замены; фразы разрешены лишь при совпадении букв после удаления пробелов. Поэтому `Привет,мир! → Привет, мир!`, лишняя запятая, исправление фразы или удаление повторного слова не доходят до редактора, даже когда провайдер их предложил.

В [main.js](../src/main.js), `registerTypoMatch` и `applyTypoReplacement`, обязательны непустые `correct` и `rawText`. Это дополнительно запрещает удаление (`correct: ''`) и чистую вставку (`start === end`, пустой исходный фрагмент). `smartPunctuation` занимается типографикой при вводе, а не проверкой грамматических запятых.

### 2. Нормализация скрывает регистр; короткие слова исключены

Сравнение нормализованных вариантов отбрасывает замены, отличающиеся только регистром или `ё/е`. Поэтому `мы → Мы` и `москву → Москву` теряются. Отдельно `collectSmartTypoMatches` рассматривает только слова длиной от трёх символов: провайдер предлагает `an → a` в `This is an test.`, но редактор не показывает замечание; аналогично короткое `go`.

Есть и расхождение двух локальных путей: при включённом обычном словаре `Вообщем` получает предложение `в общем`, теряя прописную букву. Сам Smart-адаптер сохраняет её. Этот дефект проявился в обоих профилях и уже включён в фиксированный тест.

### 3. Ранжирование теряет полезные варианты

Для `Мы читали интересную книку.` провайдер содержит `книгу`, но после сортировки по расстоянию и ограничения пятью вариантами Nocturne оставляет `книзу`, `анику`, `каику`, `кику`, `кинику`. Ошибка подчёркивается, нужного исправления в меню нет. Контекстная уместность не учитывается.

### 4. Сбой онлайна уничтожает результат локального слоя

`getSmartSpellerMatches` сначала собирает локальные исправления, затем выбрасывает исключение при сбое API и не возвращает уже готовый результат. Это подтверждено для 429, 500, 503 и разрыва сети. В редакторе при выключенном обычном словаре и включённом hybrid локальная коррекция пропадает. При включённом обычном словаре она остаётся благодаря отдельному пути — это не устраняет дефект самого hybrid.

`scheduleSpellerCheck` пишет ошибку только в консоль. Пользователь не видит, что проверка не состоялась. `Retry-After: 2` игнорируется: серия обновлений подсветки породила четыре немедленных запроса в каждом профиле. Нельзя путать такой результат с «ошибок нет».

### 5. Потеря диагностики и ограничения ресурсов

- `warnings.incompleteResults` игнорируется: непроверенные слова отмечаются проверенными.
- Замечание без предложенных замен исчезает. Например, LanguageTool отмечает несогласование `новый книга`, но не предлагает готовую замену; Nocturne скрывает сам факт ошибки.
- Восемь одновременных одинаковых вызовов делают восемь запросов вместо одного. На уровне редактора есть ограничение активного запроса, но ядро не объединяет одинаковую работу разных потребителей.
- Лимит фрагмента 4000 символов обходится одним гигантским токеном: наблюдался запрос на 10 008 символов.
- Вариант длиной 8192 символа попадает в результаты. Нужны ограничение длины/числа вариантов и проверка структуры ответа.

По коду также видно, что `provider` передаётся из интерфейса, но ядро его не использует: endpoint зашит. Для второго движка потребуется настоящий адаптер провайдера. Кэш ключуется языком и текстом, без TTL и версии правил. Эти два замечания — анализ реализации, не отдельные заявленные аварийные сценарии.

## Что работает и должно сохраниться

Unicode-позиции, повторные вхождения и преобразование координат длинного текста прошли проверки. Поздние ответы не попадают в актуальный кэш после Abort. Устаревшее исправление отвергается после редактирования. Защищённые слова и пользовательские правила имеют приоритет. Повторный отрицательный результат берётся из кэша без второго запроса. Зависший провайдер прерывается примерно через 12 секунд. Некорректные диапазоны и HTML-замены отбрасываются. Орфографическая замена сохраняет соседнее форматирование и отменяется через Undo. Не было необработанных ошибок страницы.

Новый движок должен сохранить generation/Abort-проверки, точные диапазоны, авторские исключения и транзакционное применение через редактор. Автоматически переписывать художественный текст не нужно.

## Предлагаемое улучшение

### Сначала исправить путь результата

Ввести общий формат замечания: `docId`, `blockId`, ревизия, `start`, `end`, исходный текст, тип, сообщение, `ruleId`, язык, провайдер и массив замен. Разрешить диапазоны фраз и знаков, нулевую длину для вставки, пустую строку для удаления и замечание вообще без замен. Состояние проверки хранить отдельно: проверено, выполняется, частично, недоступно.

Проверять законченные предложения/абзацы, а не очередь слов длиной ≥3. Разбивать по реальным границам с перекрытием контекста и жёстким ограничением размера; не склеивать несвязанные куски в одно синтетическое предложение. Преобразовывать UTF-16-координаты провайдера в диапазоны Tiptap, сохраняя проверку ревизии перед применением. Нормализацию словаря отделить от сравнения точного исправления: регистр и `ё` нельзя терять.

Сохранять локальные результаты независимо от онлайна. Добавить спокойный видимый статус при сбое, Retry-After/backoff, объединение одинаковых запросов, кэш по языку/провайдеру/версии правил/контексту и ограниченный срок жизни. Ограничить ответы по размерам; неполную проверку не сохранять как чистый результат.

### Второй слой: контекстная грамматика, без Hunspell

| Слой | Назначение | Ограничения и интеграция |
|---|---|---|
| Авторские правила Nocturne | Имена, неологизмы, исключения, известные опечатки | Сохранить высший приоритет и текущую защиту словаря |
| LanguageTool | Быстрые проверяемые замечания о грамматике, пунктуации, регистре и повторах | Сохранить все диапазоны; одного движка недостаточно для требуемого качества |
| Нейросетевой GEC-корректор | Согласование, управление, пропущенные/лишние знаки, контекстные ошибки | Сравнить с неизменяемым корпусом; превращать изменения в отдельные предложения автору, не переписывать рукопись |
| Проверка допустимости исправления Nocturne | Точный исходный диапазон, ревизия, защищённые имена, отсутствие перевода и лишних изменений | Это проверка безопасности применения, а не ещё один источник языковой грамотности |

[Самостоятельный сервер LanguageTool](https://dev.languagetool.org/http-server) даёт базовые правила без облачных AI-правил. Harper ограничен английским и не подходит как второй общий движок для русского и украинского. Возвращать Hunspell в эту схему не предлагается.

Для нейросетевого слоя есть два способа размещения: доступный онлайн API с ключом и квотами или отдельный локальный сервис на ПК. На Android тяжёлые модели автоматически не устанавливать: использовать подключённый сервис либо быстрый слой. Бесплатные веса модели не означают бесплатный сервер и достаточную скорость. Выбор размещения запрошен у пользователя; модель не устанавливалась.

Два проверяющих движка не следует превращать в голосование: они могут повторять ошибки. Объединять замечания по диапазонам, показывать источник, устранять дубликаты, учитывать язык и защищённые слова. Вычислять минимальные изменения между исходным и исправленным предложением; отбрасывать перевод, новые факты, изменение имён и неподтверждённые диапазоны. Стилистические предложения отделить от грамматики. Не требовать согласия LanguageTool для каждого замечания нейросети: это снова скроет случаи, которые LanguageTool пропустил. Конфликтующие исправления остаются выбором автора.

Для локальной пунктуации начать с осторожных правил пробелов возле знаков, случайных двойных запятых и парных кавычек, с исключениями для диалогов, многоточий и `?!`. Запятые перед придаточными требуют контекста: правило «всегда ставить перед что» даст ложные замечания. В корпусе LanguageTool не предложил ожидаемое исправление для `Я знаю что он вернётся.`; сохранение его ответа само по себе этот случай не вылечит.

**Приоритет:** исправить формат замечания и устойчивость hybrid → измерить второй контекстный движок → интегрировать только вариант, который улучшает грамматику и пунктуацию, сохраняя правильные фразы и стиль автора. У LanguageTool в 29 фразах отсутствует эталонный вариант; иногда есть диагностика без готовой замены. Эти случаи требуют языковых правил/иного движка, а не только изменения интерфейса.

### Проверка усиленных правил LanguageTool

Дополнительно выполнены 210 настоящих HTTP-запросов к тому же локальному LanguageTool 6.6 с `level=picky`. Корпус и эталоны не менялись. Получено **71/99** ожидаемых исправлений вместо **70/99**, грамматика **12/21** вместо **11/21**, пунктуация по-прежнему **12/25**. Единственный прирост: `Согласно приказа → Согласно приказу`. На 111 правильных контролях оба режима не дали замечаний, включая стиль. Переключение режима не закрывает основной недостаток.

Результаты: [HTML](../release/qa/app-tester/2026-10-13T08-24-22-536Z/index.html), [сводка](smart-dictionary-provider-comparison-2026-10-13.json). Синтаксис и source-integrity PASS; сравнение FAIL, поскольку оба провайдера не выполняют весь контракт. Из 420 проверок предложений 363 проходят и 57 не проходят. Это сравнение провайдеров до адаптера Nocturne.

Бесплатный тариф допускает использование контента для улучшения продуктов |

Для онлайн-варианта предлагается сначала сравнить Gemini как второй контекстный слой, используя имеющуюся архитектуру ИИ-провайдеров Nocturne, но отдельный контракт проверки. Бесплатные квоты не считать постоянным безлимитным ресурсом: запускать глубокую проверку по завершённому фрагменту/по команде, кэшировать, не делать запрос на каждое нажатие и не переключаться на платный тариф автоматически. Для полностью локального варианта сравнить специализированные GEC-модели по языкам. Ни один кандидат пока не объявлен победителем.

Изученные альтернативы не подходят как общая бесплатная замена: [TextGears](https://textgears.com/api) документирует русский, но не украинский; [Sapling](https://sapling.ai/docs/components/languages/) не документирует ни русский, ни украинский в грамматической проверке. OmniGEC имеет украинские результаты, но опубликованная таблица не подтверждает русский; у варианта 8B также нужно учитывать условия базовой Aya Expanse, а не только MIT в карточке дообучения. Покупка LanguageTool Premium сама по себе не подтверждает улучшение RU/UK: [официальный список дополнительных проверок](https://help.languagetool.org/hc/en-us/articles/39254526141463-What-languages-does-LanguageTool-support) перечисляет другие языки.

Важно: UA-GEC — корпус размеченных текстов, а не готовая программа проверки. Его можно использовать для отдельной независимой оценки после отбора модели; не подменять им текущий контракт и не подбирать правила по закрытому test-разделу.

## Неизменяемый тест для новой версии

Контракт **v1**, seed **20261013**, SHA-256 сериализованного корпуса:

```text
2998f6f511fec03f486b3d40fd69823d7727a37abea109348d0765d9c6bfd54c
```

Корпус и эталоны: [smart-dictionary-corpus.mjs](../scripts/fixtures/smart-dictionary-corpus.mjs). Записанные ответы: [smart-dictionary-provider.json](../scripts/fixtures/smart-dictionary-provider.json). Контрольная сводка и хэши: [smart-dictionary-baseline-2026-10-13.json](smart-dictionary-baseline-2026-10-13.json).

Повторить воспроизводимую часть без сети:

```powershell
node scripts/test-app.mjs --only=syntax,unit,smart-dictionary,smart-dictionary-adversarial --seed=20261013 --artifacts=off --native-android=off
```

Для реальной HTTP-интеграции сначала запустить распакованный LanguageTool 6.6 в отдельном терминале:

```powershell
java -cp languagetool-server.jar org.languagetool.server.HTTPServer --port 8081 --allow-origin
```

Затем перед тем же тестом задать:

```powershell
$env:NOCTURNE_AUDIT_LANGUAGETOOL_URL='http://127.0.0.1:8081'
```

На Windows Java-команда должна использовать `--allow-origin` без отдельного аргумента `*`: Java launcher может развернуть звёздочку в имя файла, испортив CORS. Именно это было исправлено в стенде, не в приложении. Без переменной окружения live-сценарии не выполняются; `liveIntegration.selected=false` явно отражает этот пробел, число сценариев составляет 290.

Тест поддерживает нынешнюю Map и будущий список `issues`, но смысл эталонов остаётся прежним. Новая версия должна пройти эти же фразы, правильные контроли, отказоустойчивость, позиции, редактирование и Undo; нельзя ослаблять проверки или объявлять старые ошибки ожидаемыми пропусками. Для новых провайдеров добавить отдельные закреплённые ответы, сохранив текущие. Публичные облачные правила не использовать как изменяющийся эталон.

Для независимого сравнения записанного ответа второго движка добавлен `scripts/test-smart-dictionary-provider-comparison.mjs` в единый тестер. Запись должна содержать те же 210 `id`, `text`, `lang`, SHA корпуса и версию контракта, а в каждом входе — настоящий `correctedText` либо исходный LanguageTool-совместимый ответ. Эталоны берутся из прежнего корпуса; правильные контроли проверяются на полное сохранение текста. Нельзя выбрать только удачные фразы. `NOCTURNE_AUDIT_CHECKER_RECORDING` задаёт путь такой записи; скрипт не выдумывает отсутствующие ответы. Запуск: `node scripts/test-app.mjs --only=smart-dictionary-provider-comparison --artifacts=off --native-android=off`.
