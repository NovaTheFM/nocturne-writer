## Наиболее важные результаты

1. Импорт карточки персонажа позволяет выполнить JavaScript внутри приложения.
2. Некорректный вложенный лор может записаться в базу, хотя импорт затем завершается ошибкой. Повторяющиеся ID отдельно приводят к исчезновению глав.
3. Сброс локальной базы оставляет корзину, черновики, резервные копии и служебные записи связи. Сброс настроек отключает шифрование; последующее сохранение защищённой главы пишет открытый текст.
4. Отключённый AI-контекст не предотвращает добавление лора в запрос. Применение старого AI-предложения может затереть правки автора.
5. Две вкладки могут молча перезаписать изменения одной главы. Конфликт локальной синхронизации при этом не создаётся.
6. Сервер LAN-связи можно уронить до ввода pairing code одним JSON-сообщением `null` либо слишком большим WebSocket-пакетом.
7. Умный словарь падает на неопределённом `stripHtml`; часть настроек редактора осталась подключена только к старому редактору.
8. Существующий APK и распакованная Electron-сборка расходятся с текущими исходниками по 14 веб-файлам каждый.

## 1. Баги, проблемы и несостыковки

### F01 · P1 · JavaScript из импортированной карточки персонажа

**Статус:** воспроизведено. **Область:** безопасность импорта.

**Где:** `src/main.js:18113` — `characterCard`; `src/main.js:17783` — `processImportedKbData`; `src/main.js:22694` — `validateProjectDump`.

Изображение персонажа вставляется в HTML как `src="${item.image}"` без экранирования атрибута. Импорт сохраняет строку, содержащую закрывающую кавычку и обработчик `onerror`. При открытии карточек обработчик выполняется. В тесте он только установил `window.__auditXss = true`; результат — `executed: true`, `hasHandler: true`.

Для воспроизведения достаточно импортировать тестовый `.nocturnechar`, где поле `image` содержит строку вида `missing-image" onerror="window.__auditXss=true`, и открыть персонажей. Проверка ID в полном dump не проверяет это поле; отдельный импорт базы знаний имеет ещё более слабую валидацию.

**Последствие:** чужой файл может выполнить код с доступом к данным страницы, включая расшифрованный проект и секреты активной сессии. Открытие чужого файла само по себе не должно давать ему такие возможности.

**Направление исправления:** безопасное создание DOM/экранирование каждого атрибута, проверка допустимых URL изображения и единая проверка импортируемых карточек. Рядом аналогично проверить `icon` и атрибуты ID. Это исправление поведения, а не косметическая очистка.

**Доказательство:** `release/qa/audit-probes-2.json`, сценарий `XSS from imported character portrait`.

### F02 · P1 · Ошибка импорта возникает после записи повреждённой базы

**Статус:** воспроизведено. **Область:** целостность проекта.

**Где:** `src/main.js:22694`, `src/main.js:22855`, `src/main.js:22899`; загрузка лора — `src/main.js:790`.

Валидатор проверяет верхние массивы и ID, но не форму вложенных коллекций мира. Например, `payload.lores[0].characters = { broken: true }` проходит проверку. `persistImportedProject` записывает данные через `atomicWrite`, затем `loadLore` вызывает `.map` и падает. Обработчик ошибки восстанавливает только `this.state`; запись в IndexedDB уже завершилась.

В тесте импорт отклонён с `...map is not a function`, интерфейс показывает исходную главу, а сырая запись `lore/world` уже содержит неправильный объект `characters`. Повторный запуск получает повреждённые данные. Атомарность самой транзакции здесь не защищает от ошибок последующей нормализации.

**Направление исправления:** полностью валидировать и нормализовать будущий проект до записи; обеспечить откат сохранённого состояния для ошибок после commit. Проверять все миры, а не только активный `payload.lore`.

**Доказательство:** `release/qa/audit-probes-1.json`, `nested malformed lore corrupts database despite rejected import`.

### F03 · P1 · Повторяющиеся ID в dump молча уничтожают записи

**Статус:** воспроизведено. **Область:** импорт данных.

**Где:** `src/main.js:22694`; `src/core/db.js:125` — `atomicWrite`.

Уникальность ID внутри импортируемого раздела не проверяется. Если две главы имеют один ID, обе считаются импортированными, но IndexedDB `put` второй главы заменяет первую. Тест: во входе две главы, отчёт сообщает `2`, в базе остаётся одна — `Second chapter`.

**Последствие:** потеря содержимого при формально успешном импорте. Такая же модель записи затрагивает другие разделы с повторяющимися ключами.

**Направление исправления:** проверка уникальности до любых записей; при допустимом объединении — явное переименование с корректным переносом ссылок. Числа отчёта считать по фактическому результату.

**Доказательство:** `release/qa/audit-probes-1.json`, `duplicate IDs accepted and collapse two imported chapters into one`.

### F04 · P1 · «Сбросить локальную базу» оставляет приватные данные

**Статус:** воспроизведено, включая перезагрузку. **Область:** удаление/приватность.

**Где:** `src/main.js:23602` — `performResetData`; список хранилищ — `src/core/db.js:7`.

Сброс очищает 9 из 19 хранилищ. Остаются `drafts`, `trash`, `backups` и семь `sync*`-хранилищ, включая очередь, устройства и журнал. В тесте после сброса главы пусты, но существуют приватный черновик, удалённая глава в корзине, резервная копия и записи связи.

**Последствие:** обещание удаления локальной базы не соответствует фактическому результату; прежние данные могут восстанавливаться из внутренних копий. Старая очередь/служебная информация продолжает существовать рядом с новым пустым проектом. Фактическое повторное распространение старых данных по сети отдельно не проверялось.

**Направление исправления:** определить точный контракт полного локального сброса и очищать все относящиеся к нему хранилища и ключи. Внешние файлы резервных копий — отдельный контракт, их этот пункт не требует удалять.

**Доказательство:** `release/qa/audit-probes-1.json`, `reset leaves private trash drafts backups and sync state`.

### F05 · P1 · Сброс настроек незаметно отключает шифрование

**Статус:** воспроизведено. **Область:** защита проекта.

**Где:** `src/main.js:20513` — `resetSettings`; `src/main.js:23484` — миграция шифрования; `src/core/record-protection.js:24`.

Диалог обещает сброс параметров интерфейса, редактора, AI и экспорта. Обработчик заменяет весь объект настроек на `defaultSettings`, вместе с `e2e: false`. Обычный путь отключения шифрования и миграция записей не вызываются.

Сразу после сброса старые записи могут оставаться зашифрованными. Но следующий `saveActiveDoc` уже сохраняет открытый текст. Проверка: `beforeEncrypted: true`, `afterEncrypted: false`, в сырой базе читаются заголовок и `SECRET TEXT UPDATED`.

**Последствие:** без отдельного согласия на отключение защиты формируется смесь открытых и зашифрованных записей, а новые сохранения теряют защиту.

**Направление исправления:** сохранять состояние защиты при сбросе обычных настроек либо выполнять явный согласованный переход через существующий механизм миграции.

**Доказательство:** `release/qa/audit-probes-4-confirmed.json`, `settings reset followed by saving writes formerly encrypted chapter plaintext`.

### F06 · P1 · Выключенный AI-контекст всё равно добавляет лор в запрос

**Статус:** воспроизведено без отправки внешнего запроса. **Область:** приватность AI.

**Где:** `src/main.js:20550` — `buildCurrentAiContext`; `src/main.js:20785` — `buildAiPrompt`; `src/main.js:21405` — `findRelevantLore`.

При `aiKnowledgeContext: false` построитель контекста возвращает `null`. Однако построитель prompt отдельно ищет связанные сущности и использует запасной путь `knowledgeContext || entities || ...`. Тестовая закрытая информация из персонажа попала в prompt при выключенном контексте: `context: null`, `promptContainsPrivateLore: true`.

**Последствие:** настройка, которой пользователь ограничивает передачу базы знаний, не выполняет ожидаемую роль. Есть и вторичная несостыковка: запасной путь берёт текущий мир приложения, а не обязательно мир выбранной главы.

**Направление исправления:** одна политика включения/исключения лора для всех путей формирования запроса; проверить также отдельные переключатели категорий и связь главы с миром.

**Доказательство:** `release/qa/audit-probes-2.json`, `AI lore still transmitted when context is disabled`.

### F07 · P1 · Старое AI-предложение затирает последующие правки автора

**Статус:** воспроизведено. **Область:** применение AI-правок.

**Где:** `src/main.js:21552` — `applyAssistantSuggestionPatch`.

Для замены выделения есть проверка совпадения текущего текста. Для замены целого блока исходный текст/ревизия блока не сравниваются. После получения предложения автор может дописать абзац, но применение предложения заменит весь изменённый блок старым ответом AI.

Тест: до применения `Original paragraph. New author edit.`, после — `AI replacement of original.`; операция принята с `accepted: true`.

**Направление исправления:** проверка исходного текста или ревизии для каждого типа patch и понятное разрешение устаревшего предложения. Отдельно проверить привязку позиции для продолжения текста при редактировании во время запроса.

**Доказательство:** `release/qa/audit-probes-2.json`, `stale AI whole-block replacement overwrites later edits`.

### F08 · P1 · Две вкладки молча перезаписывают одну главу

**Статус:** воспроизведено в двух страницах одного браузерного профиля. **Область:** локальное сохранение.

**Где:** `src/main.js:13900` — `saveDocById`; `src/core/db.js:95` — `put`.

Очередь сохранения существует только внутри одного экземпляра приложения. Две вкладки читают общую базу и сохраняют целую главу без проверки ожидаемой ревизии. Второй экземпляр со старым состоянием может заменить новое сохранение первого. Механизм конфликтов LAN-синхронизации это не перехватывает.

Тест: первая вкладка продолжает показывать `First tab important revision`, в базе уже `Second tab stale revision`, число `syncConflicts` — `0`.

**Направление исправления:** согласованный контракт нескольких экземпляров: проверка ревизии и разрешение конфликтов либо ограничение редактирования одним экземпляром. Уведомления между вкладками полезны, но сами по себе не заменяют защиту записи.

**Доказательство:** `release/qa/audit-probes-3.json`, `two tabs overwrite independent document edits without conflict`.

### F09 · P1 · Неподключённый клиент может уронить LAN-брокер

**Статус:** воспроизведено для Node-брокера; аналогичная ошибка Electron установлена по коду. **Область:** устойчивость/безопасность связи.

**Где:** `scripts/sync-server.mjs:108`, `scripts/sync-server.mjs:123`; `electron/main.cjs:212`.

После `JSON.parse` не проверяется, что результат — объект. WebSocket-сообщение `null` до pairing приводит к `TypeError: Cannot read properties of null (reading 'protocolVersion')` и завершению процесса с кодом `1`.

Второй путь: пакет размером `32 MiB + 1 byte` превышает `maxPayload`, WebSocket испускает `error`, но у сокета нет обработчика. Процесс завершается из-за необработанного события `error` с `WS_ERR_UNSUPPORTED_MESSAGE_LENGTH`. Слишком большой пакет должен закрывать соединение конкретного клиента, а не весь сервер.

**Последствие:** знание pairing code не требуется; достаточно сетевой доступности сервиса. В Electron такая логика находится в main process; его фактическое падение этим способом не запускалось.

**Направление исправления:** проверка формы сообщения перед чтением полей, изоляция ошибок обработчика, обработчики ошибок WebSocket и сервера.

**Доказательства:** `release/qa/audit-broker-null.json`, `release/qa/audit-broker-oversize.json`.

### F10 · P2 · Объединение dump переносит не все ссылки таймлайна

**Статус:** воспроизведено. **Область:** связи импортируемых сущностей.

**Где:** `src/main.js:22933` — `mergeProjectDumpPayload`; модель события — `src/main.js:875`.

При конфликте ID импорт создаёт новые ключи и переносит `documentIds`, `characterIds`, `locationIds`. Но `chapterIds`, `noteIds` и ключи объекта `characterRoles` не проходят преобразование.

Тест: у импортированной главы/заметки/персонажа новые ID, но событие продолжает ссылаться на прежнюю главу, прежнюю заметку и прежний ключ роли персонажа. При этом `characterIds` изменяется правильно.

**Последствие:** импортированное событие связывается с чужими существующими сущностями либо теряет доступные связи/роли.

**Направление исправления:** явная схема всех ссылочных полей, включая ключи словарей, и проверка целостности результата объединения.

**Доказательство:** `release/qa/audit-probes-3.json`, `merge preserves wrong timeline chapter and note references after ID remapping`.

### F11 · P2 · Полный импорт базы знаний теряет заметки и правила мира

**Статус:** воспроизведено. **Область:** экспорт/импорт базы знаний.

**Где:** `src/main.js:17489` — полный экспорт; `src/main.js:17783` — импорт.

Полный `.nocturnmemory` экспортирует `this.state.lore`, включая `notes` и `rules`. Ветка импорта `type === 'nocturnmemory'` обрабатывает только персонажей, локации и таймлайн, затем возвращает успешный результат. Входные заметки и правила игнорируются.

Тестовый файл содержит оба раздела; после импорта `notes: []`, `rules: []`, счётчик заметок — `0`.

**Направление исправления:** одинаковый контракт полного экспорта и импорта, явный отчёт об обработанных/неподдерживаемых разделах и проверка обратимости.

**Доказательство:** `release/qa/audit-probes-2.json`, `full knowledge import drops world notes and rules`.

### F12 · P2 · Умный словарь не запускает проверку из приложения

**Статус:** воспроизведено. **Область:** интеграция проверки текста.

**Где:** `src/main.js:11073`, конкретный вызов — `src/main.js:11090`.

`scheduleSpellerCheck` вызывает `stripHtml`, которой нет ни в импортах, ни среди определений актуального кода. При наличии слов для проверки возникает `ReferenceError: stripHtml is not defined`. Ошибка ловится, но очередь очищается, а cache остаётся пустым.

Модульные тесты самого умного словаря проходят: они проверяют функции модуля отдельно и не вызывают сломанную интеграцию из приложения.

**Направление исправления:** подключить существующее корректное преобразование текста, проверить реальный путь от набора до подсветки, сохранить возможность повторить проверку после ошибки.

**Доказательство:** `release/qa/audit-probes-3.json`, `smart dictionary throws stripHtml ReferenceError before checking words`.

### F13 · P2 · Настройки синтаксиса и слабых слов не подключены к актуальному редактору

**Статус:** воспроизведено; дополнительный дефект регулярного выражения также проверен. **Область:** настройки редактора.

**Где:** `src/main.js:10625` — `renderEditor`; `src/main.js:10895` — старое декорирование; `src/main.js:12505`, `src/main.js:12511`; набор расширений — `src/editor/nocturne-editor.js:694`.

Настройки `writerSyntax` и `showDontTell` сохраняются и показываются, но актуальный Tiptap не создаёт соответствующие decorations. На тексте с диалогом, мыслью и «очень сильно» количество `.syntax-dialogue`, `.syntax-thought`, `.weak-word` равно `0`. Старый `decorateWriterSyntax` на том же тексте создаёт нужные span. `npm run check` начинается с `build:editor`, который пишет в `src/vendor/`. Команда, воспринимаемая как проверка, может менять отслеживаемые файлы и зависит от установленной версии сборщика/пакетов.

В этом аудите она целиком не запускалась, чтобы не переписывать код. Проверка синтаксиса и тест адаптера запущены отдельно; три бандла собраны через esbuild с `write: false`. Результаты совпали с текущими файлами побайтно: Tiptap — **380 696 B**, GSAP — **95 908 B**, Capacitor — **8 331 B**.

**Направление исправления:** разделить проверку, генерацию и сравнение сгенерированных файлов; документировать побочные эффекты команд.

### F30 · P3 · Тест наложения toolbar учитывает невидимые кнопки

**Статус:** воспроизведено и уточнено вручную. **Область:** достоверность тестов.

**Где:** `scripts/test-app-motion.mjs:212`; `src/css/ui.css:1508`.

Штатный тест упал на пересечении «Обычный текст» и «Поиск и замена» в режиме «Редактор» на ширинах 1280/1440/1600. Он фильтрует только по размерам прямоугольника, не учитывая opacity/clipping предков. У скрытой кнопки остаётся прямоугольник; он и считается визуальным наложением.

Дополнительная проверка и снимок подтверждают, что форматирование невидимо, pointer events выключены. Поэтому **видимое наложение этих кнопок не включено в список подтверждённых UI-багов**. Реальный недостаток клавиатурного фокуса описан в F22.

**Направление исправления:** проверять реальные доступные hit areas/видимость и отдельно клавиатурное поведение. Не скрывать падение теста без исправления его модели проверки.

**Доказательства:** `release/qa/app-motion.json`, `release/qa/audit-probes-2.json`, уточнение `release/qa/audit-probes-4-confirmed.json`.

### F31 · P2 · Приём синхронизации многократно читает целое хранилище

**Статус:** риск производительности, установлен по алгоритму; большой проект не бенчмаркировался. **Область:** синхронизация/IndexedDB.

**Где:** `src/features/database-sync.js:134`.

В цикле каждой входящей записи локальный raw record ищется через `getAllRaw(incoming.store).find(...)`. Для N записей одного хранилища объём повторных чтений приближается к O(N²), плюс повторы при конкурирующих операциях. Маленькие интеграционные тесты это не демонстрируют как задержку.

**Направление улучшения:** адресное чтение raw-записи по ключу с сохранением существующих guards и порядка обработки. Сначала замерить реалистичный большой проект; численное ускорение в этом отчёте не обещается.

### F32 · P3 · Desktop-упаковка имеет отдельную цепочку зависимостей и не строит vendor

**Статус:** риск воспроизводимости по коду; новая сборка не запускалась. **Область:** сборочный процесс.

**Где:** `web2exe_fixed.py:59`; `package.json`; `scripts/build-web.mjs`.

Python-упаковщик создаёт отдельный `package.json` для Electron со своими диапазонами версий, запускает установку зависимостей и копирует текущий `src`. Корневая последовательность `build:editor` перед копированием им не выполняется. Корневой lock-файл не является единым источником всего этого сборочного окружения.

Сейчас vendor совпадает с пересборкой в памяти; текущий дефект vendor этим пунктом не утверждается. Но после изменения editor entry или зависимостей desktop может упаковать прежний бандл. Два пути сборки легко начинают давать разное окружение и результат.

**Направление улучшения:** единая подготовка веб-ресурсов для платформ, фиксируемые версии упаковочного окружения и проверка свежести vendor перед созданием пакета.

## 2. Что можно написать чище без изменения визуала и функциональности

Ниже **16 направлений очистки**. Исправления F01–F32 сюда не подменяются: восстановление настройки, изменение импорта, конкурентности, защиты или пагинации меняет поведение и должно выполняться отдельной задачей. Монолит `main.js` сохраняется; его разбиение на файлы не предлагается без отдельного разрешения.

### C01 · Убрать повторные определения одинаковых методов

В `src/main.js` дважды объявлены `syncFloatingMenuPortalState` (1416/23634), `buildSyncMergePreview` (2691/24023), `remoteConnectFolderTitle` (2716/24297). Последние определения затеняют первые. Изученные тела совпадают по логике, различаются форматированием.

Можно оставить действующее последнее определение каждого метода и удалить затенённое после финального структурного сравнения. Нельзя просто удалять «вторую копию» по внешнему сходству: у JavaScript уже действует последняя реализация.

### C02 · Нормализовать форматирование монолита

Особенно блок около 23600–24400: лишние пустые строки между почти каждой операцией, разный отступ, заголовки `// --- method ---`, которые повторяют название. В других местах отступы также сбиты. Это ухудшает чтение и маскирует границы try/catch.

Без изменения порядка выражений можно привести форматирование к одному стилю, убрать очевидные комментарии, оставить объяснения причин сложной логики. Не форматировать сгенерированные vendor-бандлы вручную.

### C03 · Разбить большие методы на внутренние помощники

`runAction` — около 770 строк, `handleClick` — около 583, `editLore` — около 427. Их можно сократить помощниками внутри того же класса/файла, сгруппировав подготовку данных и построение конкретных форм.

Критично сохранить порядок делегирования событий, `this`, early returns и текущую async-семантику. Замена всей цепочки действий на новый диспетчер сразу создаёт лишний риск; лучше выделять законченные ветки.

### C04 · Согласовать описания настроек в одном реестре

Настройки повторяются в `settingsContent`, `getSettingsRegistry`, `validateSettings` и defaultSettings. Названия, описания, enum и ограничения легко расходятся.

Для чистки можно централизовать существующие метаданные и генерировать нынешние представления из них. Перед переносом зафиксировать точные значения и HTML. Уже различающиеся границы/поведение нельзя незаметно «исправлять» под видом рефакторинга.

### C05 · Именованные группы хранилищ вместо повторяющихся массивов строк

Списки есть в `db.js`, `record-protection.js`, миграции шифрования, dump, сбросе и синхронизации. Сейчас они расходятся по мере добавления новых stores.

Определить отдельные именованные группы: все хранилища, защищаемые, экспортируемые, синхронизируемые и т. п. Эти группы имеют разные смыслы, их нельзя механически сделать одинаковыми. На этапе чистки сохранить текущие наборы; исправление неполного сброса F04 — отдельная работа.

### C06 · Явные формы данных и словарь ссылочных полей

Добавить полезные JSDoc-typedef для Doc, World, TimelineEvent, FloatingNote, SyncRecord, AiSuggestion и Payload. Они дадут понятную форму данных без перехода проекта на TypeScript.

Сейчас встречаются близкие, но разные поля `documentIds`/`chapterIds`, `activeLoreId` в нескольких местах и scope заметок. Типы и короткое описание назначения помогут обнаруживать несостыковки. Переименование сохранённых полей потребует миграции и уже не относится к чистке без изменения поведения.

### C07 · Уменьшить глобальную зависимость editor bridge

`NocturneEditorBridge.syncDocFromEditor` ищет документ через `window.nocturneApp`, хотя bridge уже получает callbacks при создании. Можно передать callback получения документа и использовать его, оставив идентичную выборку по ID.

Это сделает связь явной и облегчит изолированную проверку. Важно возвращать актуальный объект из state, а не хранить старую ссылку после импорта/перезагрузки моделей.

### C08 · Выделить общую сборку DOCX-контейнера

В монолите несколько генераторов XML/DOCX повторяют типы содержимого, relationships, metadata, ZIP и escaping. Можно выделить внутренние помощники для общих частей.

Нельзя попутно унифицировать разные стили, отступы, заметки или метаданные документов: это изменит результат экспорта. Проверка чистки — сравнение структуры XML и воспроизводимых частей исходных файлов, а не только «Word открыл файл».

### C09 · Упорядочить повторяющиеся таблицы меток и enum

Статусы, названия типов сущностей, scope, иконки и подписи переводятся через повторные условные цепочки в разных местах. Чистые таблицы соответствий и маленькие функции читаются проще.

Сохранить нынешние fallback-значения, порядок проверок, строки и HTML/SVG. Например, два `defaultDeviceName` сейчас возвращают разные подписи; слепое объединение поменяет интерфейс.

### C10 · Дать имена значимым константам

Вынести повторяемые размеры payload, сроки ожидания сети, интервалы, ключи storage и категории в небольшие предметные константы рядом с соответствующим кодом.

Значения и поведение таймеров оставить прежними. Не превращать каждый одноразовый числовой литерал в глобальную константу: это добавляет шум вместо ясности.

### C11 · Отделить преобразование модели от сборки HTML

Крупные формы и списки одновременно вычисляют подписи, ищут сущности, меняют state и строят длинные шаблоны. Внутренние чистые помощники для подготовки display-модели сократят повторения, а шаблоны останутся существующими.

Сохранить DOM-ключи, data-атрибуты, классы, порядок элементов и механизмы сохранения/анимации DOM. Простая замена `updateSurfaceHTML` на `innerHTML` не является безопасной чисткой.

### C12 · Проверить кандидатов на старый/неиспользуемый код

Кандидаты: `readStoredZip`, `hasHardLoreConflict` с постоянным `false`, `checkLore` с конкретным примером про Эриона, `createDeviceId` в `features/local-sync.js`, отдельный `preloader-manager.js` и Three.js, на который не найден актуальный runtime-import.

Удаление допускается только после проверки всех точек входа, динамических вызовов, платформенных сборок и скриптов. Старые функции работы с AST нельзя массово удалить: они нужны для совместимости, экспорта, анализа и части UI.

### C13 · Разделить авторский код, vendor и архивы в навигации проекта

`src/vendor` содержит сторонние библиотеки; `Useless/` — 72 архивных файла примерно на 4 MB; рядом находится отдельная `design-lab`. Можно яснее обозначить владение и назначение этих зон в документации/поиске.

Не переписывать сторонние бандлы как часть «красивого кода». Не удалять архив или design-lab без проверки назначения. Исключение ассетов из пакета — отдельное изменение сборки, с иной проверкой.

### C14 · Сделать жизненный цикл обработчиков явным

`manageModalFocus` возвращает cleanup для MutationObserver, но добавляет анонимный document keydown-listener, который cleanup не снимает. Для нынешнего единственного запуска утечка повторных обработчиков не воспроизведена.

Именованный обработчик и полный disposer сделают контракт понятнее. Аналогично можно описать владение таймерами/observer/bridge instances. Нельзя незаметно добавлять новую логику flush, задержки закрытия или менять момент сохранения: это функциональные изменения.

### C15 · Развести проверки, генераторы и экспериментальные скрипты

В `scripts/` находятся полноценные проверки и старые диагностические эксперименты. Например, `test-sound.mjs`/`test-scroll.mjs` опираются на старые селекторы/ключи и не равны официальным regression-тестам. Имена и краткое описание назначения уменьшат путаницу.

Команды проверки и сборки стоит явно различать, как описано в F29. Для будущей чистки нужны интеграционные сценарии актуального UI, а не только тесты функции, которая не вызывается приложением.

### C16 · Упорядочить CSS с сохранением каскада

Канонический `src/css/ui.css` — **327 902 B**, сумма текущих partials — **361 158 B**; legacy `src/styles.css` — **226 883 B**. В canonical CSS можно группировать связанные правила и при необходимости выделять более небольшие partials.

Нужно сохранять порядок подключения, специфичность, media-условия, переопределения и фактические вычисленные стили. Повторный селектор может быть намеренным поздним override. Сетки `.character-grid`/`.locations-grid` с `1fr` сохраняются полностью; это обязательное правило проекта. Legacy CSS удалять можно только после проверки всех потребителей, включая архивные/отдельные страницы.

Это read-only аудит исходников и изолированного веб-runtime; нативные GUI/новые сборки выходили за выбранный способ проверки и требовали бы дополнительных действий. Интернет-проверка CVE/npm audit не проводилась — актуальный статус уязвимостей сторонних зависимостей этим отчётом не устанавливается.

## 5. Рекомендуемый порядок последующей работы

1. Закрыть исполнение кода из импорта и падение брокера; отдельно согласовать модель защиты LAN-связи.
